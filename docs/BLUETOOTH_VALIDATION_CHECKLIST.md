# Bluetooth 일괄 검증 목록

## 추가 예정: HEV 연료 기준 물리 장치 검증

아래는 [새 연료 기준](HEV_FUEL_ALERT_POLICY.md)의 코드 반영 후 확인할 항목이며 이번 문서 작업에서 구현·실행하지 않았습니다.

- [ ] 차량SDK의0~100 정수 연료값이 휴대폰까지 동일하게 전달. 오류·미수신은0으로 변환하지 않음.
- [ ] HEV SOC나 차량LOW_FUEL만으로 사용자 임계값을 우회하는 알림·캐릭터가 발생하지 않음.
- [ ] +10%p 회복은 서로 다른 실제SDK조회 성공3회(응답간격>=30초·전체>=60초)로 확인. Bluetooth중복·ACK재전송은 횟수에 포함하지 않음.
- [ ] 회복 도중 무선단절·늦은이전세션 메시지는 확인완료가 되지 않음. 재연결 후 새 확인, 완료된재무장상태는 복원.
- [ ] 재알림 대기 중 임계값을 초과하면 주유필요 캐릭터는 먼저 해제. 이후 재무장·하향진입 때 알림한번.

2026-11-10 작성 당시의 미완료 목록이다. **2026-11-13~14 S24↔Tab S7 실제 무선 결과는 문서 하단에 따로 기록했다.** 아래 체크박스에는 실제 Pleos 차량/센서가 필요한 복합 항목도 있으므로 부분 통과를 전체 완료로 바꾸지 않는다.

확인된 범위: Pleos 가상 어댑터 ON, 실제 SDK 일부 콜백, 시험 프레임→저장→ACK→Android 로컬 알림 테스트. **실제 차량 앱→무선 Bluetooth→실물 휴대폰→알림은 미검증.**

## 준비 및 결과 기록

- [ ] BT-01 지원 Pleos 시험 장비/차량과 Android 실물 휴대폰 준비. [공식 AVD 안내](https://document.pleos.ai/en/docs/connect/guide/getting-started/application-development/configure-pleos-connect-emulator)의 Bluetooth 동글 미지원 확인. 폰 두 대 시험은 전송 계층 검증이며 Pleos 성공과 구별.
- [ ] BT-02 양쪽 기기/OS/API, 앱 버전·빌드 종류·커밋, SDK/서비스 버전, 시험 시각 기록. 동일 프로토콜 v2·RFCOMM UUID 사용 확인.
- [ ] BT-03 기존 프로필·관리기록 백업 및 비교 기준 확보. `install -r` 사용, wipe/앱 데이터 초기화 금지.
- [ ] BT-04 페어링은 음악/통화 연결과 구별. 앱 데이터 소켓 연결·최초 메시지 저장·ACK까지 증거 확보.

## 권한·상대 기기·연결

- [ ] BT-05 주변 기기 CONNECT 권한 허용/거부/철회, Bluetooth OFF/ON 각각 확인. 실제 위치 보완 권한은 별도 시험.
- [ ] BT-06 사용자가 선택한 페어링 상대만 연결. 다른 페어링 기기·미페어링 기기·잘못된 상대는 데이터 수신/저장 금지.
- [ ] BT-07 앱 서버 시작→휴대폰 연결→프로토콜 확인→전체 스냅샷 저장→ACK 순서. 소켓만 열린 상태를 ‘데이터 연결됨’으로 표시하지 않음.
- [ ] BT-08 상대 앱 미설치/구버전, UUID/프로토콜 불일치, 연결 대기/타임아웃의 안내와 자원 해제 확인. 같은 v2라도 구버전이 오인식 취소 필드를 처리하는지 확인하고, 최신 양쪽 빌드의 결과와 구별.
- [ ] BT-09 범위 이탈/복귀, Bluetooth OFF/ON, ACL 재연결, 수동 종료/재연결. 마지막 데이터와 마지막 수신 시각 유지. 2026-11-14 사용자 장기 자동 복구 요청 이후에는 사용자가 켠 연결 서비스 안에서만 1/3/10초 뒤 30/60/120/300초 대기 재연결을 허용한다. 고속 무한 루프·기기 검색·위치 조회·wake lock은 없으며 사용자가 종료하면 예약도 취소한다.

## 메시지·ACK·재전송

- [ ] BT-10 실제 프레임 송신→휴대폰 저장→동일 차량ID/revision ACK 왕복 확인. 빈 값/0/기본100을 임의 정상값으로 만들지 않음.
- [ ] BT-11 ACK 유실·지연·중복: 최대3회/5초 재전송, 중복 저장/알림/기록 없음. 수신 저장 후 ACK 전 단절도 포함.
- [ ] BT-12 프레임 도중 단절/잘린 프레임/과대 프레임/잘못된 JSON: 불완전 자료를 적용하지 않고 재연결 후 정상 복구.
- [ ] BT-13 같은 메시지 반복/역순/과거 revision/늦은 응답: 설정·기록·현재 경고가 과거 상태로 돌아가지 않음.
- [ ] BT-14 양쪽 앱 프로세스 종료/재시작, 재부팅 후 마지막 스냅샷·미전송 요청·중복 방지 상태 복원. 서비스 실행 조건도 실제 OS에서 확인.
- [ ] BT-15 장부128건 초과로 여러 묶음 전송. 각 묶음 저장/digest ACK 후 다음 묶음, 중간 단절·재시작에도 누락/이중 반영 없음.
- [ ] BT-16 양쪽 시계 차이/과거 시각/미래 시각/시간대 변경. 원본 관측 시각 보존, 오래된 경고를 현재 경고로 보내지 않음.

## 휴대폰 최종 설정·기록

- [ ] BT-17 첫 연결 시 기존 차량 설정 가져오기. 같은 차량의 기존 휴대폰 설정이 있으면 유지하고 기본30으로 덮지 않음. 다른 차량의 기록과 섞이지 않음.
- [ ] BT-18 차량 설정 변경 요청→휴대폰 버전 확정→차량 사본 갱신. 휴대폰 변경도 연결 중 차량에 전달.
- [ ] BT-19 단절 중 차량 변경/여러 번 편집 후 재연결, 양쪽 동시 편집/오래된 base 버전 충돌. 최신 휴대폰 설정 유지, 대기/충돌 표시와 사본 확인.
- [ ] BT-20 수동 기록 추가/수정/삭제, 자동 기록 메모 수정/수동 전환, 같은 날짜 자동+수동 보완/별도 추가 선택. ID·완료 시각·visitId 유지.
- [ ] BT-21 차량 전환/동일 visitId가 서로 다른 차량에 존재하는 경우. 설정·기록·PendingIntent·알림·취소가 해당 차량에만 적용.

## 세차 확인 배너·오인식 취소

- [ ] BT-22 업로드 기준의 시설별 조건을 충족하면 먼저 세차 반영·재계산. 장소 구분이 애매한 적격 방문은 **‘세차한 것 같아!’ / ‘세차 안 했어요’**, 전용 셀프/명확히 분리된 세차 구역은 BT-37의 완료 배너. 실제 물세차 여부의 불확실함만으로 보류하지 않음.
- [ ] BT-23 컨베이어식 N 이동→D 출차와 정차식 P/N 여부와 별개인 실제 정차180초→차량 출차를 각각 재현. 모든 시설에 N 조건을 강제하지 않음.
- [ ] BT-24 주유만 함, 주유소 대기/옆 도로 통과, 세차 구역 체류180초 미만, GPS 흔들림, 휴대폰만 남는 경우: 조건 미충족이면 기록 생성 없음.
- [ ] BT-25 휴대폰 배너/시스템 알림의 ‘세차 안 했어요’: 동일 visitId 취소, 이전 기준으로 재계산, 첫 기록이었다면 null. 앱 재시작 후에도 유지.
- [ ] BT-26 차량 배너에서 오프라인 ‘세차 안 했어요’→재연결. 설정 버전 충돌과 별개로 취소가 휴대폰에 반영되고 오래된 스냅샷으로 부활하지 않음.
- [ ] BT-27 취소→동일 방문 재전송/중복/역순, 취소 직후 앱 종료, 재부팅: 취소/알림 중복 없음. 다른 새 방문은 정상 감지 가능.
- [ ] BT-28 배너 ‘닫기’/알림 스와이프/응답 없음: 세차 반영 유지. 앱 안 배너 닫기 상태 복원, 7일 취소 기간 및 기존 기록 삭제와의 구별 확인.
- [ ] BT-29 OS 알림 허용/거부·채널 차단·방해금지·앱 알림 설정 OFF. 시스템 배너 제한과 앱 안 확인 배너를 구별. HIGH 채널이어도 실제 heads-up 표시는 OS/사용자 설정에 따름.
- [ ] BT-30 ‘기록 보기’/알림 탭/이미 앱이 열린 경우의 이동, 한글 버튼·큰 글자·다중 알림·연속 방문에서 올바른 차량/기록 선택.

## 정비 알림·화면 꺼짐·휴대폰 위치 보완

- [ ] BT-31 실제 지원 경고의 원본 상태/색상/점멸/관측 시각이 전달됨. 미확인 차종별 규칙은 자동 활성화하지 않음.
- [ ] BT-32 워셔액 부족→지속→정상→재발, 경고 악화, 이미 해제된 과거 경고의 재연결. 미지원/권한 거부/오류/단절은 정상화나 정비 완료가 아님.
- [ ] BT-33 앱 백그라운드/화면 꺼짐/절전/제조사 배터리 정책/강제 종료에서 수신·FGS·재연결·알림의 실제 범위 확인. 미보장 구간을 명시.
- [ ] BT-34 휴대폰 위치 보완 어댑터·권한·FGS 구현 후, 차량 진입→차량 신호 중단→휴대폰 유효 체류→차량 재연결·출차 연결 확인. Bluetooth 단절을 시동OFF나 세차로 해석하지 않음.
- [ ] BT-35 양쪽 위치 공백·정확도 미제공·경계 불확실·휴대폰만 시설에 남는 경우. 누락 시간을180초에 더하지 않음.
- [ ] BT-36 실제 운영에서 저장량·전송량·재전송 횟수·배터리·메모리·중복 SDK 연결 여부 측정. 기존 Gradle/AVD 성능 제한 유지.

## 제공 디자인·알림 내역·세차 확실성

- [ ] BT-37 전용 셀프 세차장 및 주유 구역과 명확히 분리된 세차 구역에서 전체 체류·유형별 패턴·출차 충족 → ‘세차 완료!’. 시설 진입만/짧은 체류는 완료 아님. 검증된 구역 정보의 출처도 기록.
- [ ] BT-38 주유와 동선이 겹쳐 애매하지만 필수 세차 조건을 충족한 방문 → 우선 반영·질문 배너. ‘세차 안 했어요’ 알림 액션/내역 액션 → 취소·점수 복원·재전송 방지.
- [ ] BT-39 제공 디자인 66종의 밝은/어두운 모드, 주유·세차·정비 조합, 복수 경고. 잘못된 부품 그림을 대신 쓰지 않으며 EV는 충전 문구 사용. 경고 미지원/자체점검/단절을 정상·수리 완료로 바꾸지 않음.
- [ ] BT-40 시스템 접힘/펼침/heads-up/잠금 화면과 실제 휴대폰 글자 크기·버튼 터치. OS 장식 영역과 제공 배너 이미지의 차이 확인. OS 설정으로 heads-up이 제한되면 별도 기록.
- [ ] BT-41 수신→내역 저장→시스템 게시 결과, 권한 거부/채널 차단/앱 설정 OFF에서도 내역 유지. 재시작·재부팅·페이지 이동·읽음 상태·취소 이력 및 차량 분리 확인.
- [ ] BT-42 동일 상태 지속/재전송→중복 없음, 명시적 정상→재발→새 알림, 여러 경고 동시 발생. 오래된 원본 시각/null 신호가 새 메시지로 갱신되지 않음, 양쪽 장치 시계 오차도 기록. 수동 완료 기록은 완료 알림, 최초 과거 기록 가져오기/메모 수정은 완료 알림 없음.
- [ ] BT-43 앱 종료/열림 상태의 알림 탭과 ‘알림 내역’ 버튼 → 해당 차량·이벤트 상세. 여러 차량/방문의 PendingIntent 혼선 없음. 알림 스와이프는 세차 취소가 아님.
- [ ] BT-44 휴대폰 알림 게시 후 정상→주유/세차/경고 등으로 런처 아이콘이 바뀌어도 이전 알림 탭·내역 액션·연결 서비스 알림에서 앱이 열림. 앱이 닫힌 경우·아이콘 전환과 알림이 동시에 발생한 경우도 확인. 에뮬레이터 회귀 검사 통과와 실물 검증을 구별.
- [ ] BT-45 여러 차량의 기록/설정/알림/캐시 분리. B를 조회하는 동안 A 수신 지속, 번호판이 같은/비어 있는 두 차량, 번호판 편집·재시작 후 동일 ID 유지. 수신 대상 변경은 명시적 확인을 거침.
- [ ] BT-46 차량/휴대폰 오프라인 기록 삭제→오래된 설정 응답·중복·역순·재연결. 수동/자동 삭제가 부활하지 않고 다른 차량을 건드리지 않음. ‘날짜 모름’은 삭제가 아니며 삭제 후 새 기록은 새 ID.
- [ ] BT-47 화면 숨김/다른 앱/화면 꺼짐 및 아이콘 갱신 OFF에서도 수신 서비스가 가능한 동안 SDK→게시→무선→폰 저장 지속. 수신 OFF·권한 거부·OS 종료·실제 무선 단절과 화면 숨김을 구별. 본 시험의 실제 무선/화면 꺼짐 부분은 미실행.

## 2026-11-13 · Galaxy S24 ↔ Tab S7 실제 무선 검사

사용자가 준비한 S24(휴대폰 역할, Android 17)와 Tab S7(차량 앱 역할, Android 13) 사이에서 **보안 RFCOMM 실제 무선**을 검사했다. 시작 소스는 `83876c3`. 일반 앱을 역할대로 설치했으며, 초기 설치 전 두 기기 모두 베모링 패키지가 없었다. 시험 표본은 일반 앱에 보내지 않고 `com.example.vemoring.phone.verification` / `com.example.vemoring.verification`에만 저장·전송했다. 재설치는 전부 `install -r`이며 데이터 초기화·프로필 wipe·페어링 초기화는 하지 않았다.

Tab S7은 Pleos 차량이 아니다. 아래에서 ‘무선 통과’는 실제 앱 전송/수신/저장/ACK를 확인했다는 뜻이며, 시험 표본의 연료·경고·주행·세차가 실제 센서에서 나왔다는 뜻이 아니다. 특히 BT-23/24/31/34/35/37/38/49/51~58의 실제 Pleos SDK·시설·시동 조건은 이번 장비로 통과 처리하지 않는다. 현재 세차 정책은 BT-53/54 및 AGENTS.md를 따르며 모든 자동 추정은 EstimatedVisit 확인 배너 경로다.

### 발견해 수정한 문제

1. **차량별 캐시와 무선 ACK 혼선:** G 차량을 받은 뒤 A의 이미 저장된 revision을 받으면 현재 캐시가 G에 남아 A 소켓에 G 차량 ID로 설정 ACK를 보냈다. 실제 무선 서버에서 `expected A but was G`를 재현했다. 이제 연결별 마지막 처리 프레임으로 ACK 차량을 결정한다. 이전 차량의 중복/오래된 프레임은 해당 차량의 기존 캐시를 선택하되 내용·revision·수신 시각을 갱신하지 않는다. 같은 무선 케이스에서 A ACK 및 기존 시각 보존을 재검사했다.
2. **권한 없이 FGS 시작:** S24에서 CONNECT 권한을 거부한 채 서비스를 시작하면 `ForegroundServiceDidNotStartInTimeException`으로 종료되는 것을 재현했다. 서비스 시작 전에 권한·어댑터 ON·주소·페어링을 확인하도록 수정했다. 권한 거부 상태로 6초 이상 유지해도 프로세스가 살아 있고 안내/캐시가 유지됐으며, 권한 복구 후 실제 무선 재연결됐다. Tab S7의 거부 안내도 재검사했다.
3. **종료 후 가짜 재시도 표시:** 블로킹 소켓 읽기를 취소하면 CancellationException 대신 IOException이 나면서, 종료된 세션이 뒤늦게 ‘재시도 중 (1/3)’을 게시했다. 재시도 계산 앞에 취소 확인을 추가했다. 실패/페어링 안내를 일반 종료 문구로 덮지 않도록 보완했고 실제 종료·미페어링 선택 후 안내가 유지됐다.
4. **빈 휴대폰 차고의 연결 진입점:** 등록 차량이 없으면 휴대폰 자체 차량 등록만 가능해 차량 앱에서 처음 가져오는 연결 동선이 없었다. 빈 차고에 ‘차량 앱에서 가져오기’를 추가했다. 사용자가 같은 차를 휴대폰에 별도 등록하도록 강제하지 않는다.

검사 도구도 갱신했다. 기존 Espresso 3.5.1은 S24 Android 17의 `InputManager.getInstance` 반사 호출에서 실패했다. 공식 수정이 포함된 Espresso 3.7.0 / AndroidX JUnit 1.3.0으로 **androidTest 의존성만** 갱신했다. 앱 런타임 SDK·최소 API·Gradle worker 제한은 유지했다. [공식 AndroidX Test 릴리스](https://developer.android.com/jetpack/androidx/releases/test).

### 재부팅·앱 업데이트 후 자동 재연결 추가 및 구버전 호환 (2026-11-14)

- 사용자 요청으로 **사용자가 켠 연결만** 기억해 자동 복구한다. `MirrorLinkSettings`에 상대 주소와 역할(차량 host/휴대폰 client)만 저장하고, 앱 화면/알림의 ‘연결 종료’ 또는 페어링 해제 때 지운다. `MirrorLinkRestoreReceiver`가 `BOOT_COMPLETED`/`MY_PACKAGE_REPLACED`에서 복구하고, 두 앱의 MainActivity 시작 때도 IO 스레드에서 같은 복구를 시도한다(이미 실행 중이면 아무것도 하지 않음). 부팅 직후 Bluetooth가 꺼져 있으면 서비스는 대기 문구만 표시하고 STATE_ON에서 연결한다. 권한이 없으면 시작하지 않으며 권한 우회·스캔·알람·wake lock은 없다. connectedDevice FGS는 Android 15의 BOOT_COMPLETED 제한 유형이 아니다. 서비스는 여전히 START_NOT_STICKY이며 OS 강제 종료 뒤에는 앱을 열 때 복구한다.
- **S24 재부팅 자동 재연결 통과:** verification 앱으로 S7에 연결해 `before-reboot` 저장과 링크 저장을 확인한 뒤 15:08:34 KST에 재부팅했다. 재부팅 중 S7에 `after-reboot`를 준비했다. 사용자는 잠금 해제만 했고 앱을 열거나 연결 버튼을 누르지 않았다. 15:09:52 첫 connect, 15:09:58 socket connected, 15:10:01 `after-reboot` 저장, 연결 알림 ‘차량 데이터 연결됨’. 재부팅 전 계측 프로세스는 재부팅으로 종료됐고 복구는 production 서비스가 수행했다.
- **앱 업데이트:** 재부팅 직후의 두 번의 `install -r`에서는 시스템이 `MY_PACKAGE_REPLACED`를 몇 분간 dispatch하지 않다가 다음 업데이트 방송이 들어오자 SKIPPED(`mBroadcastConsumerSkip`)로 처리했다. 세 번째 업데이트는 0.3초 뒤 전달되어 자동 재연결과 `after-update-2` 저장에 성공했다. OS가 방송 전달을 늦추거나 생략할 수 있어 앱 열기 복구를 추가했다. **force-stop 후 앱 열기만으로 재연결과 `after-open` 저장 통과.**
- **사용자 종료 존중 통과:** 연결 후 하네스 `disconnect`(앱의 ‘연결 종료’와 같은 `MirrorBluetoothService.stop`)를 실행하자 저장 링크가 삭제됐고, 이후 앱 열기·업데이트 모두에서 서비스가 시작되지 않았다(0개).
- **구버전(11/12 `769f570`) 휴대폰 ↔ 신버전 차량:** 구버전을 verification 앱에 downgrade 설치하면 VerificationRunner가 시험 런처를 숨긴 상태라 구버전 연결 알림이 launch intent를 찾지 못해 FGS timeout으로 종료됐다(이전 `standalone-startup-crash-preserved.txt`와 같은 시험 환경 원인, 82554bc 이후 신버전은 시작 전 검사). 셸에서 component 상태를 바꿀 수 없어, 같은 구버전 코드를 ID만 `.oldcompat`으로 바꿔 별도 설치하고 시험 차고 사본을 넣은 뒤 실제 UI로 S7을 선택했다. **신버전 S7 host의 `new-host-old-phone` 프레임을 구버전 휴대폰이 저장했고, host는 구버전의 ACK/응답을 받아 ‘휴대폰 수신·저장 응답 확인됨’을 표시했다.** 시험 뒤 `.oldcompat`은 삭제했다.
- **구버전 → 신버전 데이터 보존 통과:** downgrade 전 verification 데이터(85개 파일)를 백업하고, 구버전 실행 후 신버전으로 다시 올린 데이터와 비교했다. 시스템 파일 2개(`profileInstalled`, `ActivityThread.IDS`) 외 동일했다. 구버전 앱은 링크를 저장하지 않으므로 이 버전으로 처음 업데이트할 때는 사용자가 한 번 연결해야 이후부터 자동 복구된다.
- **미실행:** 구버전 차량 앱 ↔ 신버전 휴대폰. 차량 구버전은 시험용 앱 ID 빌드가 없고 S7에는 Pleos SDK가 없어 실제 차량 프레임을 만들 수 없으므로, 실제 탭 앱 데이터를 건드리지 않기 위해 실행하지 않았다. 실제 Pleos 차량 재시동 후 host 자동 복구도 실차에서 확인이 필요하다.

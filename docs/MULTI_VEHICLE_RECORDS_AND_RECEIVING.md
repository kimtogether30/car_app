# 여러 차량·선택 입력·기록 삭제·백그라운드 수신

기존 차량/휴대폰 자료를 유지하면서 아래 동작을 추가했다. 정비 완료 판정과 새 HEV 연료 정책은 이번 변경에서 새로 구현하지 않았다.

## 차량 등록과 선택

- 차량 앱과 휴대폰 앱에 차량 선택 및 추가 등록을 제공한다. 같은 모델에 번호판이 모두 없어도 등록별 고정 UUID로 분리한다.
- 번호판은 최초 등록·추가 등록·편집 모두 선택 사항이다. 지우거나 수정해도 차량 ID·관리기록·알림·거리 설정은 바뀌지 않는다. 비어 있을 때 예시 번호판을 실제 값처럼 표시하지 않는다.
- 차량 앱의 조회 차량과 SDK 수신 대상은 별개다. 다른 차의 기록을 조회해도 기존 수신 대상이 유지된다. ‘이 차량에 연결’에서 실제 탑승 차량과 맞는지 확인하고 수신 대상을 명시적으로 바꾼다.
- 휴대폰은 선택한 차량의 기록/설정을 표시하면서 다른 차량의 프레임도 그 차량 ID에 저장한다. 새로운 수신 때문에 조회 차량을 자동 전환하지 않는다. 마지막 프레임 하나로 다른 차량의 캐시를 덮지 않으며 재시작 후에도 차량별 캐시를 복원한다.
- 기존 단일 차량 저장본은 남겨두고 다중 차량 구조로 읽으며 첫 저장/추가 등록 때 v2 저장본을 작성한다. 기존 차량의 모델/번호판 해시를 이관 ID로 써 기존 정비·거리 장부 키를 유지한다. 신규 등록은 이 해시를 쓰지 않는다.
- 이전 휴대폰 단독 자료는 phone-local로 유지한다. 번호판/모델만 같다는 이유로 새 연결 차량과 기록을 자동 합치지 않는다. 연결 차량의 고유 ID로 별도 보존한다.

## 모름과 삭제

‘날짜 모름 (기존 기록 유지)’은 날짜를 새로 입력하지 않는 동작이다. 기존 기록을 지우거나 오늘 기록으로 바꾸지 않는다. 모름 체크를 해제하면 날짜 선택기를 열어 사용자가 날짜를 확정하도록 한다.

삭제는 관리 기록에서 해당 기록을 열고 ‘기록 삭제’→확인 창의 ‘삭제’를 눌러야 적용된다. ‘돌아가기’·창 닫기는 변경하지 않는다. 삭제된 기록은 달력/최근 기록/계산 기준에서 제외하고 이전 유효 기록을 사용한다. 삭제한 날짜를 차량 편집 화면이 다시 자동 입력하지 않는다.

동기화를 위해 삭제된 ID와 취소/삭제 표식을 보존한다. 서버 설정 버전과 별개로 명시적 삭제 의도를 처리해 오프라인 삭제가 오래된 메시지나 설정 충돌로 부활하지 않는다. 같은 ID를 새 기록으로 재사용하지 않는다. 자동 세차 삭제는 해당 방문의 확인 알림도 취소한다. 삭제는 다른 차량에 적용하지 않는다.

## 화면과 수신 수명

- ‘다른 화면에서도 차량 정보 받기’가 켜지면 기존 foreground service가 공유 Vehicle SDK 연결을 소유한다. 화면이 닫혀도 서비스 소유권이 남아 있으면 SDK 연결을 닫지 않는다.
- ‘앱 밖에서 상태 아이콘 갱신’은 아이콘만 제어한다. 이 스위치를 꺼도 차량 정보 수신 스위치는 유지된다.
- 수신 중인 차량과 다른 차량을 조회할 때도 수신 대상의 백그라운드 메시지 게시를 유지한다. SDK 연결을 두 개 만들지 않는다.
- 화면이 없는 동안 도착한 휴대폰 확정 상태도 해당 차량에만 반영한다. 다른 조회 차량의 선택을 바꾸거나 미전송 차량 편집을 덮지 않는다.
- 휴대폰의 기존 Bluetooth foreground service도 화면 표시 여부와 독립적으로 수신·저장·ACK를 수행한다.

이는 OS 강제 종료·사용자 수신 OFF·권한 거부·SDK 미지원·실제 연결 단절 상황까지 항상 수신한다는 보장이 아니다. 지원되지 않는 값을 정상/0/완료로 바꾸지 않는다. 이번 백그라운드 확인 대상은 기존 Vehicle SDK 신호와 앱 메시지 게시다. 위치 보완/구역 정확도·과거 시간별 날씨 수집·실물 Bluetooth가 완성/검증됐다는 뜻은 아니다. 지도 검색·날씨 HTTP 무한 폴링이나 새 의존성은 추가하지 않았다.

## 검증

휴대폰 API34 verification 앱에서 기존 알림·세차 취소·내역·설정·아이콘과 새 다중 차량 검사를 합쳐 **25개 통과**(`build/diagnostics/banner/fleet-phone-regressions.log`). 차량3대 등록, 번호판 공란, 차량별 기록, 다른 차 수신 중 조회 유지, 삭제 취소/확정, 오래된 삭제 메시지/별도 캐시를 포함한다. 화면 증거는 `phone-fleet-list.png`, `phone-fleet-delete.png`다.

실제 Pleos 공식 API34/4GB/2560×1440/Cold Boot에서 아이콘 갱신 OFF→실제 내비게이션 앱 표시→SOC SDK 재조회 응답 및 백그라운드 스냅샷 게시를 확인해 **1개 통과**(`fleet-background-sdk.log`,7.912초). SDK 시험 공급자나 실제 Bluetooth 성공으로 대신한 결과가 아니다. 원래 수신/아이콘 설정은 검사 후 복원한다.

차량 저장·UI 검사 **10개 통과**,15.123초(`fleet-pleos-ui-final.log`). `GarageFleetTest`, `GarageFleetUiTest`, 기존 `GarageTests`를 실행했다. 부팅 직후 첫 UI 실행에서는 Pleos 시스템 화면 재구성 중 표시 영역이 사라져1개 실패했고 나머지9개는 통과했다. 실제 앱을 열어 표시 영역을 준비한 뒤 재실행해 모두 통과했다. 검사는 별도 preference 이름을 사용하며 운영 차량에 시험 차를 추가하지 않는다.

최종 코드에서 JVM 검사는 차량33개+휴대폰29개, 총 **62개 통과**했다. 양쪽 debug APK·테스트 APK 빌드 및 lint 오류0개를 확인했다(`fleet-last-checks.log`). 차량 UI3개와 실제 백그라운드 SDK1개를 최종 APK에서 재실행해 **4개 모두 통과**했다(`fleet-pleos-last.log`,49.79초). 휴대폰 UI 캡처도 별도로 재실행해 통과했다(`fleet-phone-captures.log`). 이는 앞선 검사와 중복되므로 고유 Android 검사 수는 **36개**다.

최종 차량/휴대폰 선택 목록과 삭제 확인 화면을 실제 에뮬레이터 캡처로 확인했다(`pleos-fleet-list.png`, `pleos-fleet-delete.png`, `phone-fleet-list.png`, `phone-fleet-delete.png`). Pleos는 원래 운영 앱 화면으로 복원했다. 최초 자료 `fleet-native-before.xml`과 최종 `fleet-native-final.xml`의 저장 JSON을 비교해 기존 차량 프로필·기록이 그대로임을 확인했다. 읽기만 한 운영 자료에는 v2 저장을 강제하지 않았다.

로컬 증거 파일은 `build/diagnostics/banner/`에 보관하며 Git 제외다. 실제 무선 조건은 [Bluetooth 일괄 목록](BLUETOOTH_VALIDATION_CHECKLIST.md)의 BT-45~47에 추가했다. SDK/AVD 사양·Gradle worker 설정은 유지한다.
